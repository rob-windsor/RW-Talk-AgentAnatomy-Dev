# Build the Conference Flight Search MCP Server — Step-by-Step Guide

In this attendee exercise, you will build **`AnatomyOfAnAgentMcp`**, an independent C# **Azure Functions isolated-worker MCP server** for **Demo 5** of *The Anatomy of an AI Agent for Developers*. It exposes one MCP tool, `SearchFlights`, using fictional flight quotes. You will create the server once, test it with an MCP client, and then connect the separate `AnatomyOfAnAgent001` console application to it.

This is a **local development** exercise. No Azure deployment, airline account, or flight booking is involved. The sample data is synthetic.

## 1. Prepare your development environment

### Install the tools

On Windows, install:

1. [.NET 10 SDK](https://dotnet.microsoft.com/download/dotnet/10.0).
2. [Visual Studio Code](https://code.visualstudio.com/) and its **C# Dev Kit** and **Azure Functions** extensions.
3. [Azure Functions Core Tools v4](https://learn.microsoft.com/en-us/azure/azure-functions/functions-run-local), version **4.0.7030 or later**.
4. The **Azurite** VS Code extension (or another supported way of running the local Azure Storage emulator).
5. An MCP test client, such as the MCP client available in VS Code or [MCP Inspector](https://modelcontextprotocol.io/docs/tools/inspector). If using Inspector via its usual `npx` command, also install a supported version of **Node.js and npm**.

Verify your SDK and Functions tools in a VS Code **PowerShell** terminal:

```powershell
dotnet --list-sdks
func --version
```

You should see a .NET 10 SDK and a sufficiently recent Azure Functions Core Tools v4 version. The MCP server itself does **not** require Azure CLI login; Azure OpenAI authentication is needed only by the companion agent application.

### Understand the two processes

```text
Terminal A: AnatomyOfAnAgentMcp (Azure Functions / MCP server)
           -> http://localhost:7071/runtime/webhooks/mcp

Terminal B: AnatomyOfAnAgent001 (console agent / MCP client)
           -> discovers and calls SearchFlights over Streamable HTTP
```

Do not put `SearchFlights.cs` inside the console project. The point of this exercise is that the tool is supplied by a **separately hosted server**.

## 2. Create the Azure Functions project

The current MCP extension uses an Azure Functions **MCP Tool trigger**. The exact wizard prompts can vary by VS Code extension version, so follow the isolated-worker MCP extension path—not a generic HTTP trigger or a self-hosted MCP template.

1. In VS Code, open a new window for the server project.
2. Open the Command Palette (**F1**) and select **Azure Functions: Create New Project...**.
3. Use **`AnatomyOfAnAgentMcp`** as the project name. In this workspace, select **`C:\Dev\Community\Conferences\ESPC-Webinar-2026\Developer\Demos\AnatomyOfAnAgentMcp`** as the project folder. Create the project files directly in that folder, preserving the existing README and demo guide; do not create a nested project folder. For a standalone exercise elsewhere, use a folder named `AnatomyOfAnAgentMcp`.
4. Choose **C#**, **.NET 10**, and **isolated worker** where prompted. If your wizard cannot scaffold .NET 10 isolated worker, update the tools/templates and consult the linked Microsoft Learn tutorial before continuing.
5. Select **MCP Tool trigger** for the initial function **if available**, naming the function `SearchFlightsTool`. If the wizard offers only a generic function template, scaffold a compatible **isolated-worker** project, remove the generated sample function, then add the MCP extension and attributed `SearchFlights.cs` from this guide. You do **not** need to expose a conventional HTTP trigger. The *MCP tool name* will be `SearchFlights`.
6. Allow dependency restore to finish. Keep the scaffolded worker `Program.cs` and project SDK/package baseline; the generated `.csproj` depends on installed template versions.

Your project should have a structure similar to:

```text
AnatomyOfAnAgentMcp/
  AnatomyOfAnAgentMcp.csproj
  Program.cs
  SearchFlights.cs
  host.json
  local.settings.json
  README.md
  DEMO-GUIDE.md
  .vscode/                     # optional
```

If the wizard generated a sample function, either adapt it into the single `SearchFlightsTool` below or remove it. Avoid publishing two tools with the same MCP name.

## 3. Configure packages

From the new **server project** terminal, check dependencies:

```powershell
dotnet list package
```

The validated server used the Azure Functions MCP extension version **1.6.0**. Add it if the generated project does not already reference it:

```powershell
dotnet add package Microsoft.Azure.Functions.Worker.Extensions.Mcp --version 1.6.0
dotnet restore
```

Keep the **isolated worker** project dependencies generated by the matching Functions template. The MCP extension's documented minimums include `Microsoft.Azure.Functions.Worker` 2.1.0 or later and `Azure.Functions.Sdk` 1.0.0 or later. If your generated project differs or reports an incompatibility, resolve that against the current Azure Functions MCP documentation rather than replacing its entire `.csproj` with an unrelated example.

**Package boundary:** `Microsoft.Azure.Functions.Worker.Extensions.Mcp` belongs to this **server**. `ModelContextProtocol.Core` belongs to the **main console client** and is covered by that project's Demo 5 guide.

## 4. Configure `host.json`

Open `host.json`. Retain any compatible generated settings and configure the MCP server metadata. The validated server also used the root `telemetryMode` setting shown below:

```json
{
  "version": "2.0",
  "telemetryMode": "OpenTelemetry",
  "extensions": {
    "mcp": {
      "serverName": "ContosoConferenceFlights",
      "serverVersion": "1.0.0",
      "instructions": "Provides fictional flight quotes for the Contoso conference travel demonstration. Does not book flights."
    }
  }
}
```

The MCP extension supplies the protocol endpoint; do **not** add an HTTP-trigger function for `/api/SearchFlights` and do not manually implement the MCP transport.

## 5. Configure `local.settings.json` and Azurite

Set up the **tested** local storage configuration:

```json
{
  "IsEncrypted": false,
  "Values": {
    "AzureWebJobsStorage": "UseDevelopmentStorage=true",
    "FUNCTIONS_WORKER_RUNTIME": "dotnet-isolated"
  }
}
```

If the wizard generated additional compatible settings, preserve them. `local.settings.json` is for local development and should remain excluded from Git. Do not commit credentials if you add any later.

Start Azurite using the VS Code Command Palette (**F1 → Azurite: Start**) or your chosen emulator launcher. The **validated** setup ran with Azurite; this guide does not assume that storage-free hosting has been demonstrated for this exact server.

## 6. Implement the `SearchFlights` MCP tool

Create or replace **`SearchFlights.cs`** with the following implementation. It is adapted from the supplied server setup plan and aligned with the validated server configuration; the exact attendee scaffold and source below have **not been compiled in this documentation environment**. It uses the Azure Functions MCP trigger and four required properties. It accepts **only** the sample route/date combination, so it cannot accidentally present fictional prices as quotes for an arbitrary itinerary.

```csharp
using System.Text.Json;
using Microsoft.Azure.Functions.Worker;
using Microsoft.Azure.Functions.Worker.Extensions.Mcp;
using Microsoft.Extensions.Logging;

namespace AnatomyOfAnAgentMcp;

public sealed class SearchFlights(ILogger<SearchFlights> logger)
{
    [Function(nameof(SearchFlightsTool))]
    public string SearchFlightsTool(
        [McpToolTrigger(
            "SearchFlights",
            "Search fictional round-trip conference flights. " +
            "Returns three itineraries with economy and business-class " +
            "base fares in USD. Does not book flights.")]
        ToolInvocationContext context,
        [McpToolProperty("origin", "Origin airport IATA code (for example YYZ).", true)]
        string origin,
        [McpToolProperty("destination", "Destination airport IATA code (for example ORD).", true)]
        string destination,
        [McpToolProperty("departureDate", "Outbound date, YYYY-MM-DD.", true)]
        string departureDate,
        [McpToolProperty("returnDate", "Return date, YYYY-MM-DD.", true)]
        string returnDate)
    {
        logger.LogInformation(
            "SearchFlights called: {Origin} to {Destination}, {Departure} to {Return}",
            origin, destination, departureDate, returnDate);

        // Synthetic fixture only: no airline integration or live inventory.
        if (!string.Equals(origin, "YYZ", StringComparison.OrdinalIgnoreCase) ||
            !string.Equals(destination, "ORD", StringComparison.OrdinalIgnoreCase) ||
            !TryParseDate(departureDate, out var dep) || dep != new DateOnly(2027, 10, 12) ||
            !TryParseDate(returnDate, out var ret) || ret != new DateOnly(2027, 10, 16))
        {
            return JsonSerializer.Serialize(new
            {
                source = "Synthetic Contoso demo data",
                status = "No fixture configured for the requested route and dates",
                itineraries = Array.Empty<object>()
            });
        }

        var result = new
        {
            source = "Synthetic Contoso demo data — not real prices or availability",
            currency = "USD",
            origin = "YYZ",
            destination = "ORD",
            departureDate = "2027-10-12",
            returnDate = "2027-10-16",
            fareBasis = "Base round-trip airfare only; taxes and fees excluded",
            itineraries = new[]
            {
                new
                {
                    quoteId = "CF-101",
                    carrier = "Contoso Air",
                    routing = "Nonstop",
                    economyBaseFare = 690,
                    businessBaseFare = 1450
                },
                new
                {
                    quoteId = "CF-102",
                    carrier = "Northstar Airways",
                    routing = "One stop",
                    economyBaseFare = 540,
                    businessBaseFare = 1180
                },
                new
                {
                    quoteId = "CF-103",
                    carrier = "Lakefront Airlines",
                    routing = "Nonstop",
                    economyBaseFare = 820,
                    businessBaseFare = 1290
                }
            }
        };

        logger.LogInformation("SearchFlights returning 3 fictional itineraries with 6 fares.");
        return JsonSerializer.Serialize(result, new JsonSerializerOptions
        {
            WriteIndented = true
        });
    }

    private static bool TryParseDate(string input, out DateOnly date)
    {
        if (DateOnly.TryParseExact(input, "yyyy-MM-dd", out date)) return true;
        if (DateTimeOffset.TryParse(input, out var dto)) { date = DateOnly.FromDateTime(dto.Date); return true; }
        date = default;
        return false;
    }
}
```

Here, `[Function(nameof(SearchFlightsTool))]` names the **Azure Function**, while `[McpToolTrigger("SearchFlights", ...)]` publishes the **MCP tool name**. A client discovers **`SearchFlights`**, not necessarily the underlying function name. The third argument on each `[McpToolProperty]` attribute is a **`bool` required flag**, not a description string.

For unsupported routes or dates, the result deliberately contains no itineraries. All currency values are USD and represent **base** round-trip fares, excluding taxes and fees.

The Functions host can convert ISO date inputs into localized strings when binding them to `string` parameters. `MatchesDate` checks the structured invocation arguments instead, preserving the requested calendar date without relying on the machine's date format.

## 7. Build and start the Functions MCP server

From the **server** project directory:

```powershell
dotnet build
dotnet run
```

Leave that terminal running. This is the launch method recorded for the validated project. If the build fails, resolve the error before attempting MCP discovery. Confirm the Functions host starts and discovers `SearchFlightsTool` without an error. Its local MCP endpoint is:

```text
http://localhost:7071/runtime/webhooks/mcp
```

This is the **Streamable HTTP** MCP endpoint, not `/api/SearchFlights` and not the older `/runtime/webhooks/mcp/sse` transport. It is a protocol endpoint: opening it in a normal browser tab is **not** a meaningful invocation test.

Azure Functions Core Tools can also launch projects through `func start`, depending on the generated project. If you use that method, still verify tool discovery and invocation independently; this guide's baseline is `dotnet run`.

## 8. Test independently with an MCP client

Before involving the AI agent, make sure the **server itself** works. Use **MCP Inspector** or VS Code's MCP integration.

### Option A — VS Code MCP configuration

Create `.vscode/mcp.json` in the MCP server workspace:

```json
{
  "servers": {
    "contoso-flights-local": {
      "type": "http",
      "url": "http://localhost:7071/runtime/webhooks/mcp"
    }
  }
}
```

Start the server from VS Code's MCP integration while the Functions host remains running. Confirm it discovers one tool named **`SearchFlights`**, with the required arguments `origin`, `destination`, `departureDate`, and `returnDate`.

### Option B — MCP Inspector

Follow the [MCP Inspector documentation](https://modelcontextprotocol.io/docs/tools/inspector) to connect with **Streamable HTTP** transport and the same endpoint. Inspector is useful because you can enumerate tools and invoke them without relying on the model to choose them.

### Invoke the tool

Supply these argument values in the client:

```json
{
  "origin": "YYZ",
  "destination": "ORD",
  "departureDate": "2027-10-12",
  "returnDate": "2027-10-16"
}
```

Verify that the result contains **CF-101, CF-102, and CF-103**, with both economy and business prices. Next, try another route or date and confirm you receive **no configured fixture** rather than arbitrary quotes.

Finally, inspect the **Azure Functions host terminal**. Look for a `SearchFlightsTool` execution and a corresponding log entry, such as:

```text
Executing 'Functions.SearchFlightsTool' (...)
SearchFlights called: YYZ to ORD, 2027-10-12 to 2027-10-16
Executed 'Functions.SearchFlightsTool' (Succeeded, ...)
```

These are **illustrative log shapes**; timestamps, date formatting, invocation IDs, and prefixes vary. **Tool discovery is not proof of tool invocation.** Actual Functions execution logs confirm that your call reached the server.

## 9. Use the tool from the companion AI agent

Keep the server running in **Terminal A**, then open **`AnatomyOfAnAgent001`** in **Terminal B** and follow that project's **Demo 5** section. The client uses the C# MCP SDK (`ModelContextProtocol.Core`), creates an MCP client over Streamable HTTP, discovers `SearchFlights`, and exposes the discovered tool to Microsoft Agent Framework.

The main application's Demo 5 prompt asks for the **lowest-priced nonstop economy** itinerary for Toronto (YYZ) to Chicago (ORD) on October 12–16, 2027. With this fixture, **CF-101 ($690)** meets that criterion; CF-102 is cheaper but has one stop. When the agent also uses the other demonstrated capabilities, its worksheet can include:

| Amount | USD |
| --- | ---: |
| West Loop Hotel, 4 nights × $225 | $900 |
| Selected CF-101 nonstop economy base fare | $690 |
| **Known trip costs** | **$1,590** |
| Annual allowance $7,500 − prior spending $2,800 | $4,700 |
| **Provisional balance after known costs** | **$3,110** |

Registration, ground transportation, taxes, fees, and live availability remain unknown. The worksheet does **not** submit a travel request, grant manager approval, or book travel. The server supplies **only flight data**—the agent and its other components supply the rest.

## 10. Troubleshooting

| Symptom | What to check |
| --- | --- |
| `func` not recognized | Install/update Azure Functions Core Tools v4 and restart the terminal. |
| Worker or binding fails on startup | Confirm a compatible isolated-worker scaffold, MCP extension **1.6.0**, and worker/SDK package requirements. |
| Local storage connection fails | Ensure Azurite is running and `AzureWebJobsStorage` matches `UseDevelopmentStorage=true`. |
| Port `7071` unavailable | Stop the other host or update the port and client URL together. |
| MCP client cannot connect | Verify the Functions host is running and the URL ends in `/runtime/webhooks/mcp`. |
| Tool isn't discovered | Confirm `[McpToolTrigger("SearchFlights", ...)]`, function discovery, and the installed MCP extension. |
| Tool discovered but no function invocation logged | Call the tool explicitly in Inspector; a model may decide not to invoke it. |
| No itinerary returned | Only `YYZ` → `ORD`, `2027-10-12` to `2027-10-16` has configured quotes. |
| Wrong flight selected by the agent | Confirm the prompt says **nonstop economy**; CF-102 is cheaper overall but has a stop. |
| Worksheet omits policy or spending | Check the companion agent's knowledge search, direct spending tool, and skill; these are not server responsibilities. |

You have successfully built the server when you can **start it locally**, **discover `SearchFlights`**, **invoke it** with the supported inputs, **see the three expected fictional itineraries**, and **confirm execution in the Functions host logs**. You can then proceed to the companion agent's Demo 5 and verify the end-to-end call independently.
